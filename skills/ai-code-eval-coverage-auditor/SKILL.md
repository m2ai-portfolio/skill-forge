# AI-Generated Code Eval Coverage Auditor

As AI-generated code volume increases, the question shifts from "do we have tests?" to "are our tests adversarial enough to catch what a machine-generated code path might get wrong?" This skill audits test and eval suites against the specific failure modes that automated code generation introduces — misplaced trust, hidden state, untested error branches, and shallow happy-path coverage that passes while production burns.

## Trigger

Use when the user says "eval coverage audit", "are my tests adversarial enough", "AI code eval check", "test suite readiness", "test coverage for AI code", or asks whether their test/eval suite would catch bugs introduced by AI-generated code.

## Prerequisites

- Access to the project's test directory (e.g., `tests/`, `spec/`, `__tests__/`)
- Access to CI configuration (e.g., `.github/workflows/`, `Makefile`, `package.json` scripts)
- Access to any eval harness or golden-set files (e.g., `evals/`, `benchmarks/`)

## Phase 1: Intake

Gather:
1. **Project path** — root directory to analyze
2. **Primary language** — determines test framework conventions
3. **Known AI-generated modules** (optional) — paths generated by AI tooling; these are highest-priority targets

If not specified, analyze the entire test suite against all source files.

## Phase 2: Test Infrastructure Inventory

Map the testing landscape:

```bash
# Find test files
find <path> -name "test_*.py" -o -name "*_test.py" -o -name "*.test.ts" -o \
  -name "*.spec.ts" -o -name "*.test.js" -o -name "*_spec.rb" | sort

# Find CI config
find <path> -name "*.yml" -path "*/.github/*" -o -name "Makefile" | head -20

# Find eval harnesses
find <path> -name "eval*.py" -o -name "eval*.ts" -o -path "*/evals/*" | head -20
```

For each test file, note:
- Framework (pytest, vitest, jest, rspec, etc.)
- Approximate number of test cases
- Whether fixture/mock files exist

## Phase 3: Adversarial Coverage Gap Analysis

Check the test suite against 6 adversarial-readiness dimensions:

### G1: Error Branch Coverage
AI-generated code frequently produces happy-path-only implementations. Check:

- [ ] Every `try/catch` or `try/except` block has a corresponding test that triggers the error path
- [ ] Tests exist for null/undefined/empty inputs, not just valid inputs
- [ ] Network/API failures are simulated (not just the success case)
- [ ] Timeouts and partial responses are tested

**Signal**: Count `try` blocks in source vs error-path tests (`assertRaises`, `expect(...).toThrow`, `rescue`)

### G2: State Mutation Testing
AI code often mutates shared state silently. Check:

- [ ] Tests verify state *before and after* calls, not just return values
- [ ] Concurrent/parallel execution is tested where async code exists
- [ ] Side effects on shared data structures are tested explicitly
- [ ] Database/cache state is reset between tests (no test pollution)

**Signal**: Tests that only assert return values without checking side effects on passed-in objects.

### G3: Boundary and Edge Case Depth
AI models optimize for the training distribution. Check:

- [ ] Min/max boundary values tested (0, -1, MAX_INT, empty string, max-length string)
- [ ] Unicode, special characters, and encoding edge cases for any string processing
- [ ] Concurrent access edge cases for shared resources
- [ ] Off-by-one cases tested for any loop or index logic

**Signal**: Test inputs that are all "reasonable" values — no adversarial inputs.

### G4: Contract Enforcement
AI-generated code may silently widen or narrow function contracts. Check:

- [ ] Return type consistency tested (function never returns `null` when contract says non-null)
- [ ] Precondition violations are tested (passing invalid args should fail explicitly)
- [ ] Postcondition assertions exist (state after call satisfies invariants)
- [ ] API response shape is validated, not just status code

**Signal**: Tests that only check `response.status === 200` without asserting response body shape.

### G5: Integration Seam Testing
AI code generation often mishandles the seams between modules. Check:

- [ ] Integration tests exist that cross at least two module boundaries
- [ ] Mocked dependencies are verified against real implementations (contract tests)
- [ ] End-to-end tests exist for at least the critical user paths
- [ ] Database migrations are tested in CI (not just on manual runs)

**Signal**: Test suite is 100% unit tests with no integration layer.

### G6: Regression Guardrails
Without explicit regression tests, AI-generated changes can silently revert fixed bugs. Check:

- [ ] Bug fix commits have a corresponding test that would have caught the bug
- [ ] Flaky tests are tracked and fixed, not skipped
- [ ] Test names include the issue/ticket number for traceability
- [ ] No `.skip` or `xtest` patterns in test files without a linked issue

**Signal**: Skipped tests without documented reasons.

## Phase 4: CI Coverage Check

Inspect CI configuration:

- [ ] Tests run on every PR (not just scheduled or manual)
- [ ] Coverage thresholds are enforced (not just reported)
- [ ] Test failures block merge (not just warn)
- [ ] Eval harnesses run in CI (if present)
- [ ] Static analysis (type check, lint) runs before tests

Report any gaps as **Pipeline Gaps** separate from test gaps.

## Phase 5: Scoring

Score each dimension (0-10):

| Dimension | Score | Critical Gap |
|-----------|-------|-------------|
| G1 Error Branch Coverage | /10 | |
| G2 State Mutation Testing | /10 | |
| G3 Boundary Edge Cases | /10 | |
| G4 Contract Enforcement | /10 | |
| G5 Integration Seam Testing | /10 | |
| G6 Regression Guardrails | /10 | |
| **Adversarial Readiness Score** | **/60** | |

Readiness tier:
- **50-60**: Ready — test suite provides meaningful adversarial coverage
- **35-49**: Partial — passes review but will miss AI-specific failure modes
- **20-34**: Inadequate — happy-path coverage only
- **0-19**: Negligible — tests exist but provide no adversarial protection

## Phase 6: Report

```markdown
# AI-Generated Code Eval Coverage Report
**Project**: <path>
**Date**: <date>
**Test files found**: <N>
**Source files covered**: <N>/<total>

## Adversarial Readiness Score: <X>/60 — <Tier>

## Critical Gaps (fix before scaling AI code generation)

1. **[G1] No error-path tests for `<module>`** — 14 try/except blocks, 0 error-path tests
   Fix: Add `pytest.raises(SpecificError)` for each exception type in `<module>`

2. **[G5] No integration tests** — 100% unit tests; seam failures will reach production
   Fix: Add one end-to-end test per critical user path

## Pipeline Gaps

- [ ] Coverage threshold not enforced in CI (only reported)
- [ ] Tests run on push but not on PR (merge is not gated)

## Quick Wins (1-2 hours each)

1. Add `--fail-under=80` to coverage config
2. Add error-path test for `<top-3 untested error branches>`
3. Replace `.skip` on `<N> tests` with issue links or remove
```

## Verification

The audit is valid when:
1. All 6 gap dimensions are scored with specific evidence
2. Each critical gap has a concrete fix (not a general recommendation)
3. Pipeline gaps are listed separately from test gaps
